# Matt Auto

Drive Matt Pocock's main flow (idea → ship) end to end. You are a conductor, not a methodology: every stage is one of the vendored Matt skills, invoked as written.

The user settles the big frame in conversation *before* invoking this; what remains is implementation-level, so a **decision delegate** (a persistent subagent) answers it and the run goes unattended. The human still gets material decisions (Escalation), one look at the design after the interview (Interview gate), and a decision-graph page to push changes back through (Decision-graph report). No PR unless `--dev` / `--main` / `--pr <base>` (Ship mode); independent tickets run as Orca workers when orchestration is reachable (Parallel execution).

## Rules

- Invoke each stage's skill and follow it exactly. Do not reimplement, merge, or "improve" a stage.
- Wherever a sub-skill puts a question to "the user" — interview, seam check, ticket-breakdown quiz — route it to the delegate unless it is material. Discoverable facts are looked up, never asked.
- Do not add gates or scores the vendored skills don't define. Artifacts are theirs (`CONTEXT.md`/ADRs, the spec on the tracker, tickets) plus exactly two matt-auto reports: the decision log and the `$interview-report` decision-graph page (its `<slug>.edits.json` round-trip and its link or tab are delivery of that same page, not a third report). The unlazy ledgers under `.unlazy/` are working state, not reports. In ship mode the PR is pr-babysit's artifact.
- The shared weed-harness skills are the runtime: `$model-routing` (tiers), `$loop-report` (page build and delivery, through `$interview-report`), `$loop-gates` (unlazy). If one is missing, say `weed-harness 3.x required: <skill> missing` once on the board and use the fallback that skill names (platform subagent for every role; decision log as the only report; no gates). Never reimplement any of them inline.

## Pipeline

1. **Precondition** — record the baseline commit (`git rev-parse --short HEAD`) in the decision log; the final report measures against it. With `--spec <path>`, read the spec first: frontmatter `status` other than `confirmed` → print `spec not confirmed: run /design-map first` and stop; otherwise the log opens with `spec: <path>` and `artifact: <url>`. If `docs/agents/issue-tracker.md` is missing, run `$setup-matt-pocock-skills`. If `docs/agents/matt-auto-log/<slug>.edits.json` exists for this idea, apply those graph edits first (Decision-graph report).
2. **Select routing and probe** — automatic routing on Codex, OpenCode, and Claude Code (Model routing); never ask for an effort there. `--free` selects free-only routing on OpenCode; elsewhere report that it has no route and continue normally. On a platform with neither named agents nor model overrides, use **high** (ask only with `--confirm`). Probe Orca: `orca status --json`, then `orca orchestration run-list --json`; if `orca` fails with `bad option: --no-sandbox`, retry with `orca-ide` and use it for the rest of the run; if both fail, print `Orca unavailable: <why>` on the board and plan every wave sequential — never substitute another parallel mechanism. In the same probe, have `$interview-report` **probe** report delivery and put its answer on the board (`Report delivery: link` / `tab — <why>` / `path — <why>`), so the user learns before the gate when there will be no public link. Delivery is `deliver.py`'s job; matt-auto never runs an `orca artifacts`, `tab`, or `reload` command.
3. **Spawn the decision delegate** — one persistent Deep-route subagent (`matt-deep`; `matt-free` in free-only mode) with the big-frame summary, codebase access, and the delegate brief. On Codex use the Deep pair with `fork_turns: "none"` (the summary in the prompt replaces inherited context). Keep the same conversation alive across stages; if the platform only has one-shot subagents, carry the running Q&A log into each call. With `--spec`, the big-frame summary is the spec's `## 큰 틀` verbatim and its `## 결정` table is settled: brief the delegate to close any question the spec answers by citing the D-id, decide only the rest, and reply `ESCALATE: contradicts <D-id>` when a question needs a settled decision reversed.
4. **Interview** — `$grill-with-docs` in a codebase, `$grill-me` otherwise, one question at a time with a recommended answer, each question to the delegate. Record question → decision + rationale. A question needing a runnable answer detours via `$prototype`. When the interview ends, run `$interview-report` on the log so far and hold the **interview gate** until the user approves; nothing downstream starts while it is open. With `--spec`, the graph's first stage is `design` — the spec's decisions as read-only nodes (`source: "design-map"`, `change: "new"`, `before: null`; see `$interview-report`); a user asking at the gate to change one becomes an interview-stage `redirect` decision logged as `design override <D-id>`, and the spec file is never edited.
5. **Size branch** — fits one session (with `--spec`, one or two steps in its 구현 순서 is the signal)? Then (autonomous) write the interview log to the decision log and go straight to `$implement`; with `--confirm`, present the interview log first (the small path's only confirm). Run it as an **in-session** routed subagent, never as an Orca worker. Then the review pass (step 9), the final report, and step 10 in ship mode.
6. **Spec** — `$to-spec`, seam check answered by the delegate; it publishes the spec as written (with `--spec`, the design spec is its context). If a later confirm changes decisions, update it.
7. **Tickets** — `$to-tickets` with its breakdown quiz answered by the delegate, iterated to approval, but **hold publication** until step 8. Then plan the execution — waves, parallel or sequential, an `estimateMin` per ticket (Parallel execution) — and republish the page with the plan so the user sees how the run intends to proceed before it starts.
8. **Confirm (`--confirm` only)** — by default skip: publish the tickets as soon as the delegate approves the breakdown and write the confirm package to the decision log. With `--confirm`, present the package — interview Q&A with rationales, escalated decisions and answers, the spec reference, the ticket breakdown (title / blocked-by / delivers), the ship plan in ship mode (branch → base, PR condition), and the execution plan (waves with reasons, concurrency, placement, worktree naming `matt-auto/<ticket>`, each ticket's route → model/effort). Approval publishes the tickets; change requests rework from the affected stage and re-confirm.
9. **Implement loop** — work the frontier: a ticket whose blockers are done goes to a fresh-context subagent — "read ticket <ref>, then use $implement to build it; report open decisions back instead of guessing" — on the route Model routing assigns. Follow step 7's plan: a sequential wave runs one ticket at a time in-session; a parallel wave runs its tickets concurrently as Orca workers (Parallel execution). Per-ticket gates follow `$loop-gates`: locate unlazy once at loop start (skip gates when absent); before dispatch derive `.unlazy/matt-auto/<ticket>.GATES.md` from the acceptance criteria (one runnable gate per required outcome, manual only where no command decides); tell the subagent that ledger defines done; on return run `gate-check.mjs --reverify` yourself; unmet gates go back to the same route with the unmet ids, max two retries, then escalate as a handoff; complete only on `ALL MET`. Gates verify implementation only — design stages gain none, and gates never replace escalation. Keep `.unlazy/` ignored. **Review pass** after the last ticket: `$code-review` over `<baseline>..HEAD` (not per ticket); record each dimension as a `review.passes` entry with its finding count, fix what it confirms, re-run affected gates; in ship mode this precedes the PR. Then the final report (Decision-graph report), and step 10 in ship mode.
10. **Ship (`--dev` / `--main` / `--pr <base>` only)** — otherwise mark `⏭️ no --pr`. Ship ledger (when unlazy is installed) → verify the PR condition → push and open the PR → `$pr-babysit` in-session to merge-ready → conflicts via `$resolving-merge-conflicts` → `--reverify` the ship ledger → report. Never merge. Details in Ship mode.

## Progress board

One markdown table, identical on every platform, printed as ordinary output (1) at start, (2) at every stage transition, (3) on every escalation, (4) in step 9 whenever a ticket changes state:

| # | Stage | Skill / route | Status |
|---|---|---|---|
| 1 | Precondition | setup-matt-pocock-skills | ✅ |
| 2 | Routing | matt-* (+ Orca run_7c…) | ✅ |
| 3 | Delegate | matt-deep | ✅ |
| 4 | Interview | grill-with-docs → delegate | 🔄 Q7: error-handling seam |
| 5 | Size branch | — | ⏳ |
| 6 | Spec | to-spec | ⏳ |
| 7 | Tickets | to-tickets | ⏳ |
| 8 | Confirm | human | ⏳ |
| 9 | Implement loop | per-ticket routing | ⏳ |
| 9b | Review pass | `$code-review` | ⏳ |
| 10 | Ship | pr-babysit → matt-default | ⏭️ no --pr |

Statuses: `✅` done · `🔄` in progress with a short note (the current question, `cycle 2/5: CI red`) · `⏳` pending · `⏭️` skipped with why (`small path`, `autonomous`) · `⛔` waiting on an escalation, the gate, or an unmet PR condition. Skill / route names the vendored skill and, once known, the routed agent. Small path: 6–9 read `⏭️ small path`. During step 9 add a ticket board — Ticket · Route (model/effort for a worker) · Worker (dispatch id, worktree, environment; `—` in-session) · Gates (`met/total` from the latest `--reverify`; `—` without unlazy) · Status. Step 10's note carries the ship ledger tally. In autonomous mode append one stage-transition line per update to the decision log. The board is display only: never a file, never a stage's output, never restyled per platform.

**Every board update once tickets exist is also a republish.** "Republish" means one thing: hand `$interview-report` the regenerated data — `progress` + `tickets` and all — and let it build and publish; it keeps the route (link or tab) stable. Republish exactly when the board changes (stage transition, ticket status, gate result, escalation raised or answered) — not on a timer, not per commit. In the data: `blocked` means the run cannot proceed on that ticket now (unmet gates after retries, an escalation waiting, CI red, a merge conflict, a stopped worker) with `blocker.reason` and the checkable fact in `blocker.detail`; a ticket merely waiting on blockers is `pending` with `blockedBy`. `progress.current` is the board's `🔄` note. Every ticket node carries its route, the model/effort it resolved to, and for an Orca worker its dispatch id and worktree. Set `progress.startedAt` once, give every ticket an `estimateMin` when planning waves, stamp `startedAt` / `actualMin` as they begin and finish, and let the page derive percent and ETA — re-estimate only when you learned something, and say so in `progress.note`. The plan is published before implementation starts and stays. Fill `review` during the review pass and `pr` in ship mode (구현 → 리뷰 → PR is one picture), and put per-ticket specifics (`acceptance`, `steps`, `gateList` with `CHECK` and expected-vs-actual, `files`, `commits`) in the ticket detail. When delivery reports a tab or path instead of a link, say so once. "No link" never becomes "no report".

## Model routing (Codex, OpenCode, Claude Code)

Tiers, the model/effort pair per platform, dispatch mechanics (`spawn_agent` with `fork_turns: "none"` and `ROUTED_EXECUTION=1` on Codex, fixed-effort agents on Claude Code, packaged agents on OpenCode, `worker-start` flags for Orca), the escalation ladder, and large-context chunking live in **`$model-routing`**. matt-loop's roles:

| matt role | Tier | Claude Code agent | Use |
|---|---|---|---|
| `matt-fast` | Fast | `matt-loop:matt-fast` | Small fixes, boilerplate, mechanical edits, opening a PR |
| `matt-default` | Default | `matt-loop:matt-default` | Ordinary tickets, the babysit coordinator; the default when two routes are plausible |
| `matt-deep` | Deep | `matt-loop:matt-deep` | The decision delegate, hard tickets, conflict resolution |
| `matt-max` | Max | `matt-loop:matt-max` | Only the retry after `matt-deep` reports the problem is beyond it |
| `matt-large-context` | Large context | chunk via `matt-max` | Gemini on OpenCode; chunked Max elsewhere |
| `matt-free` / `matt-free-fast` | free-only (OpenCode) | — | `--free` only; never mix a paid route in |

Classify each ticket from what it needs, lowest clearly sufficient tier; retry one rung up when a route reports the task is beyond it (OpenCode ceiling: `matt-deep`). If a named agent or override is unavailable, fall back to the platform's normal subagent and report it — never silently switch provider or model.

## Delegate brief and escalation

Give the delegate: it answers implementation-level questions with senior-engineer judgment, preferring the asker's recommended answer unless it sees a concrete flaw; it replies with the decision plus a one-line rationale legible on its own (the log is shown to the user verbatim); and it never decides — replying `ESCALATE: <why>` instead — on security, data meaning or migration, destructive operations, externally visible interface changes, or anything contradicting the big-frame summary.

When the delegate replies `ESCALATE`, or a stage surfaces a material decision, pause, put the question to the real user with a recommended answer, feed the answer back to the delegate, and resume. Never convert an open decision into an assumption to keep moving. Autonomous mode removes routine questions, never the safety net.

## Autonomous by default (`--confirm` to opt out)

No flag needed. Routing is automatic (step 2), steps 5 and 8's confirms are skipped, and tickets publish once the delegate approves the breakdown; `--confirm` restores those gates. Step 4's interview gate is never skipped, and escalation is untouched. Write every question → decision + rationale (interview, seam check, ticket quiz, escalations and answers, implement-loop decisions) to `docs/agents/matt-auto-log/<slug>.md` as the run goes — it is the only textual record when nothing is presented live. At the end add `gates_caught: <n>` — how many gates came back UNMET on any of your `--reverify` runs this run (`—` without unlazy); that count decides the future of the per-ticket ledger. With `--spec` also add `spec_questions_reasked: <n>` — interview questions the spec had already answered (target 0). Report the log's path in the final report. (`--confirm` presents decisions live and keeps no log.)

## Interview gate (never skipped)

Right after step 4's page is generated, the pipeline stops — autonomous or not — and steps 5, 6, 7 wait for the user.

- **Deliver where the user reads.** Present exactly what `$interview-report` returned — a public URL, or the worktree's Orca browser tab plus the path, with its one-line reason when there is no link — a one-line summary of what the interview settled, and what happens on approval. The gate holds either way; an unopenable link is not a reason to run ahead, and a missing link is not a reason to skip the live board or the final report.
- **Wait.** No spec, tickets, or `$implement` while it is open; step 4 reads `⛔ interview gate`. The wait is not an escalation — do not re-ask it as a delegate question.
- **Say how to answer:** reply here, or edit/flag nodes in the page and press **수정 내보내기** (on a hosted link edits live only for that page load, so export before reloading; in the Orca tab they persist).
- **Clearing it.** A clear go-ahead (진행, ok, go) → step 5. Anything else — a terminal reply, a `<slug>.edits.json` saved into `docs/agents/matt-auto-log/`, or that JSON pasted into chat — is a change request: feed it to the delegate, rework the affected interview decisions, record it in the log, regenerate the page (same link or tab), delete a consumed edits file, present the gate again.

## Decision-graph report

The user-facing report of what got decided is never prose: it is the `$interview-report` page at `docs/agents/matt-auto-log/<slug>.html` — stages in order, decisions as editable nodes, escalations highlighted.

- **Generate** it after the interview (the gate presents it); **regenerate** it on every board update once tickets exist; **regenerate it last** with the `outcome` block and `progress.state: "done"` — after step 9's loop and gate re-verification, after the small path's `$implement`, or after step 10 in ship mode. Never earlier: a results panel written before the work is verified is a guess.
- **Round-trip.** Whenever matt-auto is invoked (step 1), or the user says mid-run they edited the graph, read `<slug>.edits.json`: every edited or flagged node is a change request. Feed it to the delegate, rework from the earliest affected stage, record it, regenerate, delete the consumed file so a stale edit is never applied twice.
- **Final report: measure, never estimate.** `git diff --numstat <baseline>..HEAD` for line counts and `git diff --name-status` for added / modified / deleted / renamed (the PR branch tip in ship mode); classify each file `code` / `docs` / `other` per interview-report's `outcome` spec with one Korean line per file; leave out `docs/agents/matt-auto-log/**` and `.unlazy/**`. Then report in the terminal, short: the link (or tab + path) first, the headline counts, tickets completed, verification results, the Run id and per-ticket dispatch ids when workers ran — and point at the graph for the decisions, never restating them as prose.

## Ship mode (`--dev` / `--main` / `--pr <base>`)

`--dev` targets `dev`, `--main` targets `main`, `--pr <base>` any base. Without one, no PR ever. Combines with `--confirm` and `--free`.

- **PR branch.** Implementation never lands on the base: at the start of implementation, if the current branch *is* the base, create `matt-auto/<slug>` and check it out; keep an existing feature branch. The name is part of the ship plan (autonomous mode takes the recommendation and logs it). All `$implement` subagents commit there.
- **PR condition.** Default: every ticket complete with its ledger `ALL MET` (or its verification passed without unlazy) and nothing escalated. A condition the user stated anywhere ("only after the full suite passes", "after #12–#14, leave #15", "not before I've seen the spec") replaces or extends the default: write it into the ship plan, encode it as gates, verify before opening, and never open while unmet — if it cannot be met in this run, stop at `⛔`, report, hand off. Whether it is satisfied is measured, never the delegate's call; ambiguous → escalate.
- **Ship ledger (unlazy installed).** Before opening the PR write `.unlazy/matt-auto/ship.GATES.md` with two groups, runnable wherever a command decides: *PR condition* — G1 every ticket ledger `ALL MET` (`for f in .unlazy/matt-auto/*.GATES.md; do [ "$f" = .unlazy/matt-auto/ship.GATES.md ] || node <gate-check> --reverify "$f"; done`, expect no UNMET), G2 one gate per user-stated condition; *Merge-ready* — G3 the PR exists against the base (`gh pr view <branch> --json baseRefName`), G4 required checks pass (`gh pr checks <pr> --required`), G5 `mergeable == MERGEABLE`, G6 no reviewer requesting changes (`reviewDecision` in APPROVED|NONE|REVIEW_REQUIRED). A condition no command can decide is a manual gate whose evidence is the user's explicit answer. You authored the commands, so approve the ledger yourself; fill `<pr>` after opening; `--reverify` before opening (PR-condition group MET), after every babysit cycle, and before reporting. Wire failures to the machinery: G4 → babysit's fix cycle, G5 → the conflict bullet, G6 → address the review. A stop that is not merge-readiness becomes `ABANDON: <id> <reason>` — an honest handoff.
- **Open, babysit, resolve.** Push the PR branch (plain push, never force) and `gh pr create --base <base>` with title and body from the spec and tickets, normal PR unless asked otherwise. Invoke `$pr-babysit` exactly as written, in-session on the Default route (`ROUTED_EXECUTION=1; use $pr-babysit on PR <n> and shepherd it to merge-ready`); its stop conditions apply, and a stop that is not merge-ready ends step 10 as a handoff with the URL and unmet items. On unmergeable, `git merge origin/<base>` in the isolated worktree, dispatch `$resolving-merge-conflicts` with `ROUTED_EXECUTION=1` on `matt-deep` (`matt-free` in free mode; if unavailable, stop rather than pay), run the checks, commit, push normally; never rebase or force-push, never resolve in the caller's checkout; repeat within babysit's cycle bound if the base moves again.
- **Merge-ready, not merged.** Done means required checks green, `mergeable == MERGEABLE`, no changes requested — proven by *your own* `--reverify` printing `ALL MET`; pr-babysit's report is input. If they disagree, the ledger wins. matt-auto never merges.
- **Routing.** Opening the PR → `matt-fast`; babysit coordinator → `matt-default`; conflict resolution → `matt-deep`. Without automatic routing, the platform's subagent at step 2's effort, conflicts at `high` or above.
- **Report** adds: PR URL, base, PR condition and how it was verified, ship ledger tally, babysit cycles, commits pushed during babysit, final check state, merge-ready or not. Autonomous mode logs the same.

## Parallel execution (automatic)

No flag turns it on. Step 2 probes Orca; step 7 plans waves; step 9 runs each accordingly. Only *where implementation workers run* changes — steps 1–4 and 6–8, the delegate, and every gate keep their meaning. `--parallel N` (default 2, max 4) and `--on <env>` override concurrency and placement.

**Planning waves (step 7)** — your call, recorded as the page's `plan` block, every wave with the reason it is shaped that way. Start from `$to-tickets`' blocking edges; keep a candidate wave **sequential** when its tickets touch the same files or section, when one's design changes the other's assumptions, when a ticket is exploratory, or when merging back would collide — DAG independence is not disk independence. Cap a parallel wave at the concurrency; prefer fewer, wider waves; give every ticket an honest `estimateMin`. With Orca unreachable every wave is sequential and `plan.note` says why — a sequential plan is still published.

**Workers buy concurrency and isolation; anything that runs alone runs in-session.** Orca orchestration (Run → Task → Dispatch) dispatches a parallel wave and only that: the small path, a sequential wave's tickets, a one-ticket wave, and step 10's babysit stay in-session routed subagents. matt-auto is a *supervised* coordinator — the `orchestration` skill's supervised path (`run-create → task-create → worker-start → check --wait`), never `orca-cli`'s full handoff, never a non-Orca subagent tool for workers (no Orca provenance; `task-list --json` / `dispatch-show` is what proves orchestration). Preconditions: `orca status --json` shows a running runtime and `run-list --json` answers (orchestration enabled in Settings › Experimental); `orca-ide` when the shim fails; every new shell binds the Run with `run-use --id <run>` first (else `run_required`); `--on <env>` naming an unlisted environment is escalated. Route each ticket with Model routing and translate the tier into `worker-start` flags per `$model-routing`'s Orca table (in `--free` mode only `matt-free*`, never a Claude or Codex worker).

**The loop (step 9):**

1. `run-create --objective "<spec title>" --json` once, then `task-create --spec "<worker prompt>" --deps '[<blocker task ids>]' --json` per ticket. The worker prompt is the in-session one plus the Orca lifecycle lines in `orca-worker-prompt.md` next to this file. Print the Run id on the board.
2. For each ready ticket (`task-list --ready --brief --json`), up to the concurrency: `orca worktree create --name matt-auto/<ticket> --json` parented on the working/PR branch (remote: `new-top-level` with an explicit `--repo` after pushing the branch); write the ticket's ledger into that worktree (`CWD: ../..` on every gate, regex expectations in `/…/`) and approve it there (approvals bind the ledger's absolute path); pre-trust the worktree for Claude Code (`~/.claude.json` `projects` with `hasTrustDialogAccepted: true`, else readiness fails with `codex-trust-workspace`); then `worker-start --task <id> --worktree path:<worktree> <route flags> --json`. Remote workers approve their own copy; the evidence that counts is produced locally.
3. Wait with `check --wait --types worker_done,escalation,question --timeout-ms 900000 --json` — never sleep/poll. A timeout or `{count:0}` is a checkpoint; heartbeats and visible activity mean alive. Process the whole Delivery, then `check --ack <delivery_id> --wait …`. A `question` goes to the delegate and back via `reply --id <msg_id>`; `ESCALATE` and `escalation` go to the user.
4. On `worker_done`, verify — the report is a signal: `gate-check.mjs --reverify` on the ledger in the worker's worktree (remote: fetch the pushed branch and reverify in a local temporary worktree). Unmet → `send --to dispatch:<id> --subject "unmet: <ids>"` (max two retries, then handoff) and `task-update` the task back to `dispatched` so the DAG does not advance. On `ALL MET`, `git merge --no-ff` into the working/PR branch (a conflict is resolved right there via `$resolving-merge-conflicts` on `matt-deep` in-session), copy the ledger into the main checkout's `.unlazy/matt-auto/` and run `--approve --reverify` there, and `--reverify` every previously completed ticket's ledger on the merged code. Only that second `ALL MET` completes the ticket and unblocks dependents. Then `worker-release --dispatch <id> --json`.
5. `worker-start` may return `failed` at `dispatch_input` with `agent_prompt_stalled` although the prompt was delivered. Read the terminal; if the TASK block is there and the agent works, do **not** retry — keep waiting on `check --wait`, its report arrives as `Rejected worker_done`, verify as in 4, `task-update --id <task> --status completed` yourself, close the terminal with `worker-stop`/`terminal close`. Note the stall on the board.
6. Recovery: `worker-show` `ready` → keep waiting; `failed`/`stopped` → `worker-start --task <task> --retry-of <id>` with explicit `--worktree` and agent; `outcome_unknown` → `worker-stop`, inspect, retry. Never abandon a worker for a timeout, idle TUI, heartbeat, or question. If the session is lost, `run-list` → `run-use` and rebuild the frontier from `task-list`.

Step 10 stays in-session; release the Run's workers before it begins. unlazy boundaries are `$loop-gates`': one Solo ledger per ticket, Orca owns dispatch and retry, unlazy owns gates and evidence, never unlazy's Parallel/Orchestrated mode or its Stop hook alongside Orca. Add the Run id, dispatch ids, worktrees, placements, and merge order to the final report and the decision log; release every worker before reporting unless the user asked to keep one.

## Fallback

- No subagents on the platform: run human-in-the-loop — every sub-skill question goes to the user, step 8 is to-tickets' own approval, behave as if `--confirm` was passed.
- Delegate lost mid-pipeline: respawn it with the Q&A log so far.
- Shared weed-harness skill missing: see Rules.

## Red flags — you are drifting off the flow

- Answering a sub-skill's question yourself, asking the user about non-material decisions, or converting an open decision into an assumption → the delegate decides the routine, the user decides the material, nobody assumes.
- Re-asking a decision the `--spec` file already settled, or letting the delegate reverse one → the design stage is settled; a reversal is an escalation, and a user's change at the gate is a logged redirect.
- Starting the spec, tickets, or `$implement` while the interview gate is unanswered, or publishing tickets before step 8's confirm in `--confirm` mode → those are the gates the user keeps.
- Letting the page or the board go stale, marking a ticket `blocked` without the checkable reason, dropping the live board or the final report because the link was refused, or running `orca artifacts` / `tab` / `reload` yourself → the page is the user's window into a run they are not watching, and delivery has one owner.
